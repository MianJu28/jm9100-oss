## 10. 根因定位（2026-11-02 16:00）：顶点着色器里 RGBA32F 的 `texelFetch` 只返回前两个分量

### 10.1 结论

**顶点着色器中对 128 位（RGBA32F）纹理的 `texelFetch` 只返回 `x/y`，`z/w` 被丢成 `(0, 1)`。**
同一个纹理对象、同一个纹素，在**片元着色器**里完全正确；`isampler2D`（RGBA32I）在 VS 里也正确。
这解释了火狐"页面图元全不可见、只剩底色"：WebRender 的 brush 顶点着色器从
`sPrimitiveHeadersF` / `sRenderTasks` / `sGpuCache`（全是 RGBA32F）取矩形 `(p0.x,p0.y,p1.x,p1.y)`
与颜色，拿到的是 `(x, y, 0, 1)` → `rect_clamp` 把几何夹成退化矩形（实测覆盖 1169/4096）、
颜色也变成 `(r,g,0,1)`；canvas/PDF 走合成器表面路径、不经过这条取样，所以照常显示。

### 10.2 最小复现（不含任何 WebRender 代码）

- VS：`/tmp/wrshade/min/vt.vs.glsl`（8 行，`uniform highp sampler2D sGpuCache;` +
  `dbg = texelFetch(sGpuCache, ivec2(0,0), 0);`，纹理为 RGBA32F，`texel(0,0)=(0.3,0.6,0.9,1.0)`）
- FS：`/tmp/wrshade/min/passthru.fs.glsl`（`oFragColor = dbg*0.5+0.5`）
- 运行器：`/tmp/wrreplay`（`cc -O1 -o /tmp/wrreplay /tmp/wrreplay.c -lEGL -lGLESv2`）

| 驱动 | `PT(32,32)` | 说明 |
|---|---|---|
| mwv207 | `(166,204,128,255)` | z = 0.0（应为 0.9→242） |
| llvmpipe | `(166,204,242,255)` | 正确 |

同一纹理同一纹素：VS 路径 mwv 丢 z/w，FS 路径正确（`sPrimitiveHeadersF texel(2,0)` 真值 `(-1,-1,1,1)`：
VS mwv `(0,0,128,255)` vs VS llv `(0,0,255,255)`，FS 两边都 `(0,0,255,255)`）。

### 10.3 源码机制（三处，均已实证）

1. `src/mwv207-umd/drivers/mwv207/nir/mwv207_lower.c` 的 `mwv207_lower_128bit()`：
   `if (nir->info.stage != MESA_SHADER_FRAGMENT) return;` ——把"4x32 位纹素取样拆成两次 64 位取样"
   的 pass（`mwv207_lower_tex_128_impl()`）**限制在片元着色器**。VS 里的 4x32 位取样因此保持单条
   指令（反汇编 `TEXLD_U_S_L r1, s0, …`），硬件只回 64 位；FS 里同样取样会被拆成
   `TEXLD r1.zw, s1.xxxy` + `TEXLD r1.xy, s0.xyxx` 两条。
2. `mwv207_lower_tex_128_impl()` 内部写死 `ctx->info.tex_record[PIPE_SHADER_FRAGMENT][...]`。
3. `src/mwv207-umd/drivers/mwv207/mwv207_draw.c` 的 `mwv207_update_shader()` 只为
   FRAGMENT/GEOMETRY/TESS_CTRL 调用 `mwv207_set_current_shader()`；**VS 只在
   create/bind shader_state 时选一次**，之后再不会因为采样器视图变化而重编译。
   实测日志（插桩 `[L128DBG]`/`[SAMDBG]`）：
   `lower_128bit 入口: stage=0 tex_128bit=0` → `set_sampler_views stage=0 num=1 views128=1`
   → 说明 VS 编译发生在采样器视图绑定**之前**，且此后永不重编译。
   另外 `mwv207_sampler.c` 的 `set_sampler_views()` 原来每次绑定都把全局
   `ctx->info.tex_128bit` 清成 false，即"最后一个绑定的 stage 说了算"。

## 11. 根因确认与修复（2026-11-02）

### 11.1 根因

火狐在 X11/EGL 下用 **GLES 3.0** 跑 WebRender，其 brush 顶点着色器全靠
`texelFetch` 从 `RGBA32F` 纹理（`sGpuCache` / `sPrimitiveHeadersF` /
`sRenderTasks`）取图元的矩形与颜色。本驱动把"一次 128 位取样拆成两次 64 位
取样"这套降级**只对片元着色器生效**：

```c
/* src/mwv207-umd/drivers/mwv207/nir/mwv207_lower.c（修复前） */
static void
mwv207_lower_128bit(nir_shader *nir, struct mwv207_context *ctx)
{
   if (nir->info.stage != MESA_SHADER_FRAGMENT)
      return;
   ...
```

于是顶点着色器里对 RGBA32F 的 `texelFetch` 只拿到 x/y，**z/w 被丢弃并换成
(0, 1)**。WebRender 取到的 `p1 = (x, y, 0, 1)`，矩形被夹成退化几何；颜色也
只剩 `(r, g, 0, 1)`。片元着色器里同样的取样是正确的，所以"FS 强制输出红色时
整页能变红"，只有真正依赖 VS 取数的那条路径失效。

### 11.2 三处配套修改

1. `nir/mwv207_lower.c`：拆分管控从"只允许 FRAGMENT"改为"只排除 KERNEL"；
   `mwv207_lower_tex_128_impl()` 与 `mwv207_exchange_texture_swizzle()` 全部按
   `stage` 参数化（后者改成返回 `bool`，视图为 NULL 时调用方必须 `continue`，
   否则会把未初始化的 `mov` 插进 IR → 段错误）。
2. `mwv207_sampler.c`：`ctx->info.tex_128bit` 原来在入口清零、再按"本次绑定"
   置位 —— 谁最后绑谁说了算，而实际顺序是 VS 先绑 FS 后绑，于是 VS 编译时
   看到 0。改为循环结束后跨所有 stage 重算。
3. `mwv207_draw.c`：`mwv207_update_shader()` 原来只给 FS/GS/TCS 重核对 shader
   key，VS 只在 create/bind 时选一次 → 采样器视图变化后永不重编译，上面两条
   改了也不生效。

### 11.3 一并修掉的潜伏缺陷（崩溃）

"让 VS 重编译"暴露了原驱动里一直存在的内存破坏：同一个
`struct mwv207_shader` 会被重编译多次，而 `infile` / `outfile` / `link` 这三份
"本次编译产物"挂在 shader 上、填充时用累加语义
（`sf->num_reg = MAX2(sf->num_reg, idx + 1)`、`sf->reg[sf->num_reg++]`），
跨次编译只增不减 → `num_reg` 越过 `reg[0x10]` 的边界，把紧随其后的 `link`
和 `code` 指针一起覆盖。core dump 现场：

```
(outfile).num_reg = 25          # 数组只有 16 项
shader->code = (uint32_t *) 0x2300000003
#6 mwv207_record_code (...) at nir/mwv207_compiler.c:388   # FREE(shader->code)
#7 mwv207_compile_shader (...) at nir/mwv207_compiler.c:459
#8 mwv207_set_current_shader (...) at mwv207_shader.c:997
#9 mwv207_update_shader (...) at mwv207_draw.c:1105
```

修复：`mwv207_compile_shader()` 里每次编译前 `memset` 这三份记录，并释放上一轮
的立即数表（`mwv207_record_uniform()` 每次都重新 MALLOC，不释放就泄漏）。

### 11.4 关于 PIPE_CAP_MAX_VARYINGS

曾尝试把 `PIPE_CAP_MAX_VARYINGS` 从 8 提到 16（GLES 3.0 规定的最低是 15 个
varying 向量，且驱动自己声明了 `MAX_INPUTS=16`）。实测 16 个 `vec4` varying
会撞上驱动自己的断言：

```
mwv207_compiler.c:619: mwv207_link_shader:
  Assertion `next_shader->infile.num_reg < 0x10' failed.
```

说明内部 IO 记录只有 16 个槽（且一个 varying 可能占多个槽），声明 16 属超额
声明。**保持 8**，并在代码里写明原因。火狐在 8 下已能正常渲染。
